# Облік закупівель

Вебзастосунок для обліку закупівель за договорами: що замовили, що приїхало, що ще очікуємо.

**Стек:** NestJS (BFF/API) · React + TypeScript (Vite, React Router, TanStack Query, Recharts) · PostgreSQL 16 (TypeORM, pg_trgm).

## Можливості

- **Договір (замовлення)**: номер, контрагент, дата договору, орієнтовна дата поставки, файл договору, примітки.
- **Найменування** у договорі: кількість, одиниця виміру, необов'язкова **ціна за одиницю** (для сум в аналітиці).
  Для кожного рахуються **отримано** (сума поставок), **не зможуть** (з причиною) і
  **очікуємо** = замовлено − отримано − не зможуть. Приклад: замовили 100, отримали 20, 20 не зможуть → очікуємо 60.
- **Поставки**: дата, номер накладної, скан, кількість по кожному найменуванню (не більше, ніж очікується).
- **Пошук**
  - глобальний (Ctrl+K або «/» будь-де): договори, найменування, поставки, файли, контрагенти — з групуванням
    і підсвічуванням; сторінка `/search` з повними результатами;
  - у списку договорів — рядок пошуку + розширені фільтри (дати договору / орієнтовної поставки / фактичних
    поставок, стан — кілька одразу, сума й кількість від–до, є файл / недопоставка / поставки), сортування,
    сторінки, збережені пошуки, експорт у CSV. Усі фільтри — в адресі сторінки (можна поділитися посиланням).
  - Слова — у будь-якому порядку і в різних полях запису; без урахування регістру; кирилиця/латиниця
    («М8» = «M8»), і/ї, е/є, апострофи (’ ʼ ') і лапки не заважають; допускаються одруківки (pg_trgm);
    слово-дата (15.09.2026) шукається і серед дат.
- **Аналітика** (`/analytics`): KPI (кількість і сума договорів, отримано/очікуємо, прострочені, недопоставки,
  частка вчасних поставок), розподіл за станами, контрагентами, періодами (місяць/квартал/рік), топ найменувань,
  своєчасність поставок, найбільш прострочені договори. Фільтри — ті самі, що й у списку. Таблиці — у CSV.
- **Вхід і ролі**: `admin` (усе + користувачі й журнал), `editor` (зміна даних), `viewer` (лише перегляд).
  Сторінка входу, зміна власного пароля, керування користувачами (створити, роль, вимкнути, скинути пароль).
- **Журнал дій**: входи (успішні й невдалі, IP, браузер), виходи і **всі зміни даних** з різницею «було → стало»;
  перегляд для адміністратора з фільтрами та історія змін на сторінці договору.

## Структура

```
apps/api         NestJS: REST API під /api, роздає зібраний фронт у продакшені
  src/auth         вхід, сесії, guard ролей, захист від підбору пароля
  src/users        керування користувачами
  src/audit        журнал дій (тригер у БД + контекст транзакції), історія договору
  src/contracts    договори; contract-query.ts — спільний фільтр (список, аналітика)
  src/deliveries   поставки
  src/files        файли (на диску, метадані в БД)
  src/search       глобальний пошук
  src/analytics    агрегати для аналітики (SQL)
  src/health       GET /api/health для k8s-проб
  src/common       валідація, SQL-збирач, розбір пошукового запиту, контекст запиту
apps/web         React + Vite
  src/lib          API-клієнт, форматування (uk-UA), стан в адресі, CSV, нормалізація пошуку
  src/auth         контекст користувача, RequireAuth / Can
  src/components   каркас (меню, пошук), фільтри, тости, діалоги, таблиці, журнал
  src/pages        сторінки
packages/shared  TypeScript-типи контракту API, спільні для бекенду і фронту
```

### Конвенції API

- Усе під `/api`, усе (крім `POST /api/auth/login` і `GET /api/health`) вимагає входу (cookie сесії).
- Без `@Roles(...)` діє політика за замовчуванням: читати (GET) — будь-яка роль, змінювати — `admin`/`editor`.
- Списки з пагінацією повертають `Page<T>`: `{ items, total, page, pageSize }`; параметри — `page`, `pageSize`, `sort`, `dir`.
- Помилки валідації — `422` з `{ errors: { "items.0.quantity": "..." } }`; ключ `_` — загальна помилка.
  `401` — немає сесії, `403` — недостатньо прав, `429` — забагато спроб входу.
- Зміни даних — лише в транзакціях (`ds.transaction` або `save/remove`): так тригер журналу знає автора.

## Запуск

### Docker Compose (застосунок + PostgreSQL)

```bash
docker compose up --build
```

Відкрийте http://localhost:3000 і увійдіть як `admin` / `admin-password` (див. `docker-compose.yml`).

### Розробка

Потрібні Node.js 20+ і PostgreSQL з базою `orders`.

```bash
npm install
ADMIN_LOGIN=admin ADMIN_PASSWORD=admin-password \
DATABASE_URL=postgres://postgres:postgres@localhost:5432/orders npm run dev:api   # API на :3000
npm run dev:web                                                                   # фронт на :5173 (проксі /api → :3000)
```

Таблиці створюються міграціями автоматично при старті API. Завантажені файли — у `data/uploads`.

### Змінні середовища

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `DATABASE_URL` | так | рядок підключення до PostgreSQL |
| `SESSION_SECRET` | у продакшені | ключ HMAC для ідентифікаторів сесій, ≥ 32 символів (`openssl rand -base64 48`) |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | для першого запуску | перший адміністратор — створюється, лише якщо користувачів ще немає |
| `ADMIN_NAME` | ні | ПІБ першого адміністратора |
| `COOKIE_SECURE` | ні | cookie лише по HTTPS (за замовчуванням `true` при `NODE_ENV=production`) |
| `SESSION_IDLE_HOURS` / `SESSION_MAX_DAYS` | ні | строк сесії без активності (12 год) / максимальний (30 днів) |
| `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCK_MINUTES` | ні | блокування облікового запису після N невдалих спроб (5 / 15 хв) |
| `LOGIN_IP_ATTEMPTS` | ні | ліміт невдалих спроб з однієї IP за 15 хв (30) |
| `TRUST_PROXY` | ні | довіра до `X-Forwarded-For` (за замовчуванням приватні мережі) |
| `PORT`, `UPLOADS_DIR`, `MAX_UPLOAD_MB`, `WEB_DIST` | ні | порт, каталог файлів, ліміт розміру файлу, каталог фронту |

**Чому серверні сесії, а не JWT:** сесію можна миттєво відкликати (вихід, вимкнення користувача, скидання
пароля), не потрібні refresh-токени й чорні списки, а застосунок і так працює однією реплікою з БД.
У cookie (`httpOnly`, `SameSite=Lax`, `Secure`) — випадковий 256-бітний токен, у БД — лише його HMAC.

### Продакшен-збірка без Docker

```bash
npm run build
DATABASE_URL=... SESSION_SECRET=... npm start   # http://localhost:3000
```

## Перевірки

```bash
npm run typecheck
createdb orders_test
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/orders_test npm test
```

Тести API працюють з окремою базою, яку **повністю очищують** перед кожним файлом тестів.

## Зміни схеми БД

Міграції — у `apps/api/src/database/migrations` (TypeORM). Нову міграцію додайте туди ж
і в перелік `migrations` у `database.module.ts`. Нові таблиці з даними підключайте до журналу:
`CREATE TRIGGER <таблиця>_audit AFTER INSERT OR UPDATE OR DELETE ON <таблиця> FOR EACH ROW EXECUTE FUNCTION audit_row()`.
Нормалізація пошуку — SQL-функція `search_norm()` (міграція `Search`) і її дзеркало
`apps/web/src/lib/search-norm.ts`; тест звіряє їх між собою.
